# Changelog

All notable changes to TideWM are documented here. Format loosely follows [Keep a Changelog](https://keepachangelog.com/).

## [0.54.0] - 2026-07-21

### Added
- **Three new `[[rule]]` keys (Phase N tier 2): `no_focus`, `position`, `size`.** `no_focus = true` maps a window without stealing focus (niri's `open-focused false`) -- whatever was focused before stays focused, rather than picking some other window instead. `position`/`size` (`<x>x<y>`/`<width>x<height>`, same syntax `[[output]]`'s `position` already uses) give a floating window an exact placement/size on map, matching Hyprland's rule `move`/`size` effects -- no-op unless the window actually ends up floating (from `float`/`pin`/the auto-float heuristic), applied via new `Smallvil::apply_floating_placement`, the same configure+`map_element` shape `retile()`'s own tiled loop and the interactive resize/move grabs already use.
- **`master_orientation` config key (Phase N tier 2).** `left`/`right`/`top`/`bottom` (default `left`, matching the previous hardcoded behavior) -- which side the master pane sits on under `default_layout = master`. `top`/`bottom` stack the other windows horizontally in the remaining strip, matching Hyprland's own actual behavior for those two rather than a naive 90-degree rotation of left/right. Hyprland's niche `center` variant was skipped outright -- no analog need surfaced for it. One global setting (not per-workspace, unlike `master_ratio`, which is interactively adjusted). `layout::layout_master_rects` unit-tested for all four orientations.
- **`workspace_auto_back_and_forth` config key (Phase N tier 2, niri's own feature of the same name).** Off by default; when on, re-selecting the already-active workspace jumps back to whichever one was active immediately before it instead of no-opping. `Smallvil::workspace_previous` tracks the per-output previous workspace on every real `switch_workspace` call, the same reserved-tag shape `scratchpad_previous` already uses for the scratchpad's own toggle.
- **`toggle-dpms` action (Phase N tier 2).** Wraps the existing `wlr-output-power-management-v1` machinery (`Smallvil::set_output_power`, previously only reachable from an external client like `wlopm`) as an ordinary bindable WM action, matching both niri (`power-off-monitors`) and Hyprland (`dpms`) treating this as bindable rather than external-tool-only. Toggles every output together (if any is on, turns all off; otherwise turns all on) so a multi-monitor setup can't end up half-on from one press.
- **`cursor_hide_after_ms` config key (Phase N tier 2, niri's `cursor.hide-after-inactive-ms`).** udev backend only: hides the software cursor after this many milliseconds of no real pointer motion. `0` (default) disables it. Independent of `cursor_always_visible` -- that overrides a *client's* own hide request, this is a separate compositor-driven idle timer, and the two can be combined. `Smallvil::note_pointer_motion` (called from both `PointerMotion`/`PointerMotionAbsolute` handling in `input.rs`) records `last_pointer_motion` and arms a single wake-up timer the first time it's needed (`cursor_idle_timer_armed` guards against spawning a fresh calloop timer source on every one of a real mouse's hundreds-per-second motion events); the timer re-reads `last_pointer_motion` on each fire and reschedules itself further out (`TimeoutAction::ToDuration`, the same self-extending idiom `winit.rs`'s own redraw timer uses) if motion happened more recently than expected, rather than trusting its own original delay. It only requests a redraw -- `backend/udev.rs::render_surface` re-derives the actual hide/show decision fresh from `last_pointer_motion` every frame, so a slightly early/late timer fire can't itself produce a wrong result.
- **`bsp_split_bias` config key (Phase N tier 2, Hyprland dwindle's `force_split` idea).** `auto` (default, unchanged) is the existing aspect-ratio-driven per-split axis choice; `horizontal`/`vertical` force every BSP split one way regardless of window/output shape. A single `layout::split_axis` helper is now the one place that decides a split's axis -- `split()`'s own geometry and the `Axis` metadata `hit_test`/`collect_resize_splits` report both route through it, so the two can't drift apart the way this project's Z-order invariant once did across two independent call sites. Verified live in a nested session: unit-tested (`split_axis_auto_follows_aspect_ratio_but_bias_overrides_it`) plus `grim` screenshots confirming a forced `horizontal` bias produces a side-by-side split on a taller-than-wide output where `auto` would have stacked it, a live config-reload correctly re-splits an existing two-window tree in both directions, and removing the key entirely falls back to the unchanged adaptive default.
- **`workspace_name` config key and name-addressable `workspace:<name>`/`move-to-workspace:<name>` (Phase N tier 2, niri's `set-workspace-name`, Hyprland's `workspace name:foo`).** `workspace_name = <N> <name>` (repeatable) aliases a name onto an existing numbered workspace; the workspace's real identity stays its number -- this is purely an addressing convenience, not a second identity, matching this project's static-numbered `Layouts` model rather than adopting niri's dynamic one. `config::WorkspaceRef` (`Number`/`Name`) keeps `parse_action` a pure string parser with no `Config` to check a name against -- resolution happens at the point of use (`Smallvil::resolve_workspace_ref`), the same split responsibility `bsp_split_bias` and every other config-dependent action already follows. An unknown name warns and no-ops, the same convention an invalid numeric workspace used before names existed. Verified live over IPC/`tidectl`: `workspace web` switched to the aliased workspace (confirmed via the `outputs` query's `active_workspace`), a window spawned there correctly reported that workspace number, `move-to-workspace:chat` moved the focused window there, and `workspace doesnotexist` correctly no-opped with a logged warning instead of switching.
- **`layer_rule { namespace = ... block_capture = true }` (Phase N tier 2, the last item in that tier -- niri's `layer-rule { block-out-from ... }`).** Lets a sensitive layer-shell surface (a password-manager quick-access panel, say) opt out of screenshots and screencasts by namespace, without hiding it from the user's own screen -- a genuine privacy feature, and both capture protocols (`wlr-screencopy-unstable-v1` and `ext-image-copy-capture-v1`) already funnel through the exact same render/readback function (`capture.rs::render_one_capture`), so this is one code path, not two to keep in sync. Rather than reimplementing Smithay's internal `space_render_elements`/`render_output` layer-ordering logic just to omit specific surfaces (real render-path work, the same tier as the still-deferred fullscreen-above-layer-shell gap), a matched surface's rect is instead blacked out (opaque `[0,0,0,255]`) in the client-visible copy, after the real pixels have already been read back into CPU-only memory but before that data reaches the client's SHM buffer -- the practical result a client sees is identical either way, without touching the render path at all. `config::LayerRule::matches` is a case-sensitive namespace substring match (rofi's own namespace is literally `"rofi"`); a rule with no `namespace` never matches anything, same "blank rule matches nothing" precedent `WindowRule` already set. Unit-tested (`layer_blocks_capture_matches_by_namespace_substring_only_when_flagged`, `logical_rect_to_buffer_scales_location_and_size_together` -- the latter catching that a fractional output scale must round, not truncate, or an excluded rect ends up one pixel short at an edge) and verified live in a nested session against real `rofi`: with a `namespace = rofi` rule, `grim` run *as a TideWM client* (through TideWM's own `wlr-screencopy`, not the host's) showed a solid black rectangle exactly where rofi's drun menu was, while the live frame (screenshotted from the host, i.e. what a real user actually sees) showed rofi's real content completely unaffected the whole time; removing the rule via a live config reload made the very next capture show rofi's real content again, confirming the feature is genuinely opt-in and reload-reactive, not a standing behavior change.

### Added
- **`raise-window`/`lower-window` actions** for the focused floating window (no-op on a tiled one, same restriction `toggle-pseudo-tile` uses in reverse). `lower_window` has no direct `Space` primitive to call, so it raises every *other* floating window instead, preserving their relative order -- the same trick `retile()` already uses to keep floating windows above the tiled layer.
- **`cycle-focus` (Alt-Tab) is now most-recently-used order, not `Space` z-order.** `Smallvil::focus_history` tracks every window that's held keyboard focus, updated from `reconcile_keyboard_focus` and pruned on window destruction; a window `cycle_focus` has never seen before (freshly mapped, never focused) falls back to `Space`'s own order, appended after every known entry. **A real bug caught before this shipped, not by `cargo test` (which cannot see this class of thing): reordering history on every cycle step made a 3+ window cycle degenerate into an A/B two-window oscillation** -- each press moved whatever it just focused to the front of the MRU list, which the next press then read back as "current," permanently skipping every window beyond the second-most-recent. Fixed with `Smallvil::cycling_focus`, a flag suppressing the history reorder for the duration of `cycle_focus`'s own `focus_window` call, so a whole cycle sequence walks one stable snapshot instead of reshuffling mid-walk. **Verified live**, not just traced: launched this build nested inside the machine's real (older) TideWM session, spawned three real `kitty` windows over IPC, and confirmed six consecutive `cycle-focus` presses correctly walk win3→win2→win1→win3→win2→win1→win3 -- all three windows reachable, no oscillation. Also exercised in the same live session with no crash or warning: `toggle-floating`, `raise-window`/`lower-window`, `focus-urgent` with nothing urgent, `windows`/`focused-window` JSON output including the new `urgent` field, and a clean `quit`.
- **Urgent-window concept.** `Smallvil::urgent` plus a `focus-urgent` action to jump straight to whichever window is asking for attention, exposed as an `urgent` field on the `windows`/`focused-window` IPC queries (and `tidectl`'s formatted output) for a bar to read. Wired to a real signal rather than left for later: a *stale*-serial xdg-activation request (previously refused outright, silently dropping the request) now still mints its token and marks the requesting window urgent instead of stealing focus once the token is consumed -- matches niri's own downgrade-to-urgency behavior. A missing serial entirely stays unconditionally trusted, unchanged from before: xwayland-satellite/notification-daemon activations can never carry a Wayland seat serial at all, and downgrading *those* would silently break every X11 app launch (the exact regression Phase I already found and fixed once).
- **Auto-float heuristic for dialogs and fixed-size windows.** A newly-mapped window with a parent (`ToplevelSurface::parent()`, e.g. an about/preferences dialog) or whose min/max size are equal and nonzero (a splash screen, a fixed-size utility panel) now floats by default instead of tiling and stealing half the screen -- both niri and Hyprland do this. A new `rule { tile = true }` window-rule key is the escape hatch back to tiled per app, the one flag in `WindowRule` that means "force tiled" rather than "force floating." Not live-verified this pass -- needs a real dialog-spawning client, same standing caveat as the rest of `map_toplevel`'s untested-in-isolation logic.
- **No-modifier floating-window edge resize.** A plain left-drag on a floating window's own edge pixels now resizes it directly, matching niri and Hyprland -- previously any floating resize needed `Super`+right-drag (still works, unchanged, always resizes from the bottom-right corner). `input::floating_resize_edge` hit-tests the click against the window's rect using the same border-threshold convention `layout::hit_test_split` already uses for tiled split boundaries; unit-tested directly (interior click, each single edge, both diagonal corners).
- **Touchscreen support (`wl_touch`).** `Seat::add_touch()` (unconditional, same "just advertise it" precedent as pointer/keyboard/`wp-pointer-gestures`) plus `InputEvent::TouchDown/Motion/Up/Frame/Cancel` handling in `input.rs`, adapted from anvil's own touch handling but without anvil's parallel `update_keyboard_focus` re-implementation -- TideWM already has its own centralized focus authority (`reconcile_keyboard_focus`) that a second focus-setting path must not bypass. Deliberately pure protocol forwarding for this pass, matching this project's other recently-added input protocols (`wp-pointer-gestures`, `wp-keyboard-shortcuts-inhibit`): a touch doesn't raise/focus the window under it, doesn't drive any WM action, and doesn't start a move/resize grab -- it only delivers `wl_touch` events to whatever's already there, real gesture/tap-to-focus integration is a follow-up if it turns out to matter. `Smallvil::touch_location` maps a touch event's normalized position onto logical space the same way `PointerMotionAbsolute` already does (first output, no per-device binding) rather than anvil's own "prefer eDP" heuristic, for consistency with this codebase's existing absolute-pointer convention. Unlike relative pointer motion or touchpad gestures, this isn't structurally blocked from nested testing -- Smithay's winit backend does forward real `WindowEvent::Touch` from the host -- but this pass had no real touch hardware to actually test with either way; needs real hardware (prompted by the maintainer's own ThinkPad T14 touchscreen).
- **Windows tiled on a disconnected output now migrate to a fallback output** instead of sitting unreachable in an orphaned `Layouts` entry (a real, previously-documented gap -- see the Multi-monitor section of AGENT.md). `Smallvil::migrate_output_windows` moves each window to the same workspace *number* on the first still-connected output, reusing `Layouts::remove`/`insert` rather than trying to graft one BSP tree onto another. Scope for this pass: tiled windows only -- floating windows on a disconnected output are a separate, still-open gap this doesn't cover. Not live-tested (needs real multi-monitor hotplug hardware), same standing caveat as every other cross-output feature in this file.

## [0.52.1] - 2026-07-21

### Fixed
- **`[input.touchpad]` can now be hot-reloaded for an already-connected touchpad**, not just a newly-plugged one. `apply_touchpad_config` used to run only from the `DeviceAdded` path; a laptop's built-in touchpad never fires that again short of a restart, so an edited setting silently didn't take until the compositor relaunched. `Smallvil::known_touchpads` now holds a cloned handle (libinput's `Device` is cheaply ref-counted `Clone`) to every touchpad-class device seen, populated/pruned on `DeviceAdded`/`DeviceRemoved`, and `reload_config` re-applies the current `[input.touchpad]` settings to all of them.

## [0.52.0] - 2026-07-21

### Added
- **Waves, TideWM's own config format, replaces TOML entirely.** `config.wave` (was `config.toml`) is now a hand-rolled, line-based syntax instead of TOML: `key = value` is the rest of the line after the first `=` (so `spawn:$wave(rofi -show drun, wofi --show drun)` needs no string-quoting for a command with its own flags/spaces), a line ending in `{` opens a real multi-line block (no inline `output eDP-1 { position = 0x0 scale = 1.0 }` on one line -- this is the one deliberate departure from looking exactly like Hyprland), `#` comments unless inside quotes. `bind <combo> = <action>` replaces `[keybinds]`/`"combo" = "action"` table entries; `submap <name> { }`, `output <name> { }`, `rule { }`, `input { touchpad { } }`, `xwayland { }`, `env { }`, `switch_events { }` replace their TOML table/array-of-table equivalents. `include "path.wave"` (repeatable, one per line) replaces the `include = [...]` array, with identical merge semantics carried over exactly: input/touchpad/env/switch_events/submap sections merge field-by-field across files (includer wins per key), output/rule blocks just accumulate -- ported at the `waves::Entry` level (`src/waves.rs`) instead of `toml::Value`, tested against its own grammar in isolation.
- **`$wave(a, b, c, ...)`**, a built-in alongside `$name` variable substitution: resolves to the first candidate whose own first word is a real, executable file (checked directly or via `$PATH`), falling back to the last candidate untried if none resolve, so a spawn still gets attempted and fails visibly rather than silently doing nothing. Makes the *shipped default config* actually portable across machines -- `terminal = $wave(kitty, alacritty, foot, xterm)` in `DEFAULT_CONFIG_WAVE` picks whatever's actually installed instead of hardcoding one binary name the way the old TOML default (and Hyprland's/sway's own defaults) always have.
- **`cursor_always_visible` config key** (udev backend, default `false`): forces the software cursor to stay visible even when a client asks to hide it (`CursorImageStatus::Hidden`) -- e.g. a terminal hiding its own pointer glyph after inactivity. Off by default since respecting a client's own hide request is the correct behavior; this is an opt-in override for anyone who wants the pointer to never disappear.

### Fixed
- **`wl_output` global leak on monitor disconnect** (found in 0.51.2's real-hardware testing): `create_surface` discarded the `GlobalId` from `create_global`, so unplugging a monitor left the global advertised forever and a replug stacked a second one on top. `SurfaceData` now keeps the id and retracts it in `handle_connector_change`'s `Disconnected` branch.
- **Infinite retry loop on a GPU fence wait error** (`backend/udev.rs::render_surface`): the fence-wait loop treated every error as transient and retried forever; per `eglClientWaitSyncKHR`'s own spec the only error it can return is a non-retryable invalid sync object, so a persistent bad fence would have hung the only event-loop thread permanently -- the same class of freeze as the 0.15.1 `TileMoveGrab` deadlock. Now tries once and presents whatever the swapchain already has.
- **`PointerMotionAbsolute` panic when no outputs are mapped**, reachable during shutdown if a host compositor delivers a final absolute-motion event after outputs are already torn down.
- **`WlrForeignToplevelState::cleanup_closed` is now actually wired into both backends' per-frame cleanup tick**, matching what its own doc comment already claimed. Not an active leak today (`untrack` already removes its own entry synchronously on every close), but a documented safety net that wasn't hooked up.
- **A defensive fix for 0.51.2's reproduced-once Overview stacked-text bug**: the shared glyph-advance loop in `overview.rs`/`tab_strip.rs`/`toast.rs` had no floor on a 0-advance-width glyph, which could draw the rest of a string in a near-vertical column instead of a line. Floored to `.max(1.0)` in all three. Not independently re-confirmed against the hardware that originally reproduced it.
- **`pseudo_tile_scale`'s doc comment now matches its actual `[0.05, 1.0]` clamp range.**

### Security
- **Session-lock auto-unlock-on-crash was considered and rejected.** 0.51.2 flagged that a lock client dying without a clean `unlock_and_destroy` leaves no in-session recovery. Auto-unlocking on client death was evaluated and rejected: it reintroduces the exact vulnerability `ext-session-lock` exists to prevent (killing the locker to reach the desktop). The current fail-locked behavior stays as-is; a safer future fix would respawn a locker rather than drop to the unlocked desktop.

## [0.51.3] - 2026-07-21

### Fixed
- **`wl_output` global leak on monitor disconnect**, found in 0.51.2's real-hardware testing pass: `create_surface` discarded the `GlobalId` from `create_global`, so unplugging a monitor cleaned up TideWM's own state but left the global advertised forever, with a replug stacking a second one on top. `SurfaceData` now keeps the `GlobalId` and `handle_connector_change`'s `Disconnected` branch calls `remove_global` with it. winit's own equivalent discard is left as-is (documented, not a bug there: its single simulated output never disconnects mid-process).
- **Infinite retry loop on a GPU fence wait error** (`backend/udev.rs::render_surface`): `while let Err(e) = element.sync.wait() { retry }` treated every error as transient, but per `eglClientWaitSyncKHR`'s own spec the only error it can return is an invalid sync object -- not transient, despite Smithay naming the error type `Interrupted`. Looping on it forever would hang the only event-loop thread (including VT-switch handling) permanently, the same class of freeze the 0.15.1 `TileMoveGrab` deadlock caused. Now tries once and presents whatever the swapchain already has instead.
- **`PointerMotionAbsolute` panic when no outputs are mapped** (`input.rs`): reachable during shutdown if a host compositor delivers a final absolute-motion event after outputs are already torn down. Now drops the event instead of unwrapping.
- **`pseudo_tile_scale`'s doc comment matches its actual clamp range now** ("(0, 1]" was never what the code did; it's always been `[0.05, 1.0]`).
- **Wired up `WlrForeignToplevelState::cleanup_closed`**, whose own doc comment already said it ran from the per-frame cleanup tick -- it didn't. `untrack()` already removes its own entry synchronously on every close today, so this is a safety net rather than an active leak, but it's cheap and now matches what the comment promised.
- **A timeboxed, reasoned attempt at 0.51.2's reproduced-once Overview stacked-text bug**: `overview.rs`/`tab_strip.rs`/`toast.rs`'s shared glyph-advance loop (`pen_x += metrics.advance_width.round() as i32`) had no floor, so a 0-advance-width glyph (zero-width joiners, combining marks, `.notdef` fallback -- window titles are arbitrary text) would stall `pen_x` near the label's start while `glyph_y0` kept varying per character, drawing the rest of the string in a near-vertical column instead of a line. Floored to `.max(1.0)` in all three places. Not independently re-confirmed against the hardware that reproduced the original bug -- see `AGENT.md` for the caveat.

### Security
- **Session-lock crash recovery was considered and deliberately not implemented.** 0.51.2 flagged that a lock client dying without a clean `unlock_and_destroy` leaves the session locked with no in-session recovery. Auto-unlocking on client death was evaluated and rejected: it would reintroduce exactly the vulnerability `ext-session-lock` exists to prevent (an attacker killing the locker to reach the desktop). The current fail-locked behavior (blank fill stays up, VT-switch is the recovery path) is the secure one and is staying as-is.

## [0.51.2] - 2026-07-21

### Tests
- **Real multi-monitor hardware testing, first time ever:** plugging a real second monitor (HDMI) into a live session was correctly detected (`tidectl outputs` immediately showed the new output, correct mode/position). **Found a real bug, not yet fixed:** unplugging it does not retract the corresponding `wl_output` Wayland global, even though TideWM's own internal state is correctly cleaned up -- `backend/udev.rs:875` discards the `GlobalId` `create_global` returns, so the disconnect handler has nothing to call `remove_global` with. Confirmed two independent ways in the same session: `grim` failing to capture the disconnected output ("failed to copy output HDMI-A-1"), and `hyprlock`'s own debug log showing three bound outputs (`eDP-1` once, `HDMI-A-1` twice) after one unplug/replug cycle. A user-run `fastfetch` reporting "3 monitors" during the same session, initially assumed to be `fastfetch`'s own quirk, turned out to be entirely accurate. See `AGENT.md`'s Multi-monitor section for the fix.
- **`ext-session-lock-v1` verified live end to end against a real lock client for the first time:** `hyprlock` locked correctly and the user unlocked with their real password back to a fully working desktop. Reading Smithay's own session-lock source directly surfaced a real, still-open gap while doing this: nothing unlocks the session automatically if the lock client dies without a clean `unlock_and_destroy`, and TideWM's own client-disconnect handler is a no-op -- the realistic recovery from a crashed lock client is killing the whole compositor session, not just the dead client. Flagged in `AGENT.md`, not fixed (`hyprlock` itself never actually crashed during testing).
- **More real keybinds confirmed via actual keypresses:** `Super+N`/`Escape` (submap enter/exit), `Super+V` (toggle-floating, isolated test window), `Super+F` (toggle-fullscreen). `wp-cursor-shape-v1`'s actual on-screen glyph confirmed changing shape between contexts when the pointer is kept moving -- the one verification gap Phase L's original pass couldn't close nested.

## [0.51.1] - 2026-07-21

### Fixed
- **`show_welcome_hint`'s "delete the key to dismiss" advice actually did nothing.** `RawConfig`'s struct-level `#[serde(default)]` falls back to `RawConfig::default()` for any omitted field, and that default was `true` -- so deleting the key from an existing config just silently reverted to showing the hint again, the opposite of what its own on-screen text told you to do. Default flipped to `false`; first-run behavior is unaffected since the auto-generated template always writes the key explicitly as `true`.

### Tests
- **Real-hardware verification pass** (t14arch, AMD Renoir/Vega, real udev/DRM backend, live session): confirmed working end to end for the first time -- `wlr-output-power-management-v1`'s real DRM CRTC power toggle (screen visibly blanked and recovered via `wlopm`, no freeze, matching risk class to the historical `TileMoveGrab` 0.15.1 incident but clean this time), `zwlr_gamma_control_manager_v1`'s real DRM gamma ioctls (`wlsunset` produced a user-confirmed visible warm color shift), the actual `Super+9`/`Super+1` workspace-switch keybind path via a real physical keypress (not just the underlying function), pseudo-tiling's visual result via `grim` (correct, matches design), and `toggle-pin` (confirmed to set both `floating` and `pinned` and to survive a workspace switch). Also reconfirmed, definitively this time: `wtype`/virtual-keyboard input structurally cannot trigger WM keybinds (delivers straight to the focused client, bypassing the keybind filter by protocol design) -- literal text/Return delivery works fine, modifier-combo keybinds never will via this path, on this or any future session. PSS held flat ~49-51MB over ~30 minutes of active mixed real use, no leak. Full write-up, including two real-but-not-yet-root-caused bugs found live (Overview's window-label text occasionally rendering as a stacked column of characters for a non-active workspace; the software cursor appearing to vanish from the real screen after ~2-3s of inactivity) and two non-TideWM findings (a QuickShell `-c`/`-p` config-selection gotcha; this machine's physical brightness keys producing zero Linux input events at the kernel level), is in `AGENT.md`'s "Real-hardware verification pass" section.

## [0.51.0] - 2026-07-21

### Added
- **First-run welcome hint**, Hyprland's own default-config idea adapted to this project's existing CPU-composited-texture pattern (`src/welcome.rs`, same approach as `toast.rs`/`overview.rs`). A persistent "fake window" card ("Welcome to TideWM", `Super+Enter` opens a terminal, how to dismiss) renders centered on any output whenever the desktop is genuinely empty -- built once at startup, no timer, no fade. It disappears the instant a real window maps, the same way Hyprland's own hint gives way to your first window, and comes back if the desktop empties out again (closing everything) unless dismissed for good.
- **`show_welcome_hint` config key** (default `true`) is the dismiss mechanism: delete the line, or set it `false`, and it stops showing -- checked on every reload, not just at startup, unlike the one-shot toast this replaced during the same pass.
- **Default terminal changed from `weston-terminal` to `kitty`.** `weston-terminal` was a "rarely actually installed" placeholder by its own comment; `kitty` is what this project's own default config examples already assumed everywhere else.
- **Real CLI flags: `-c`/`--config <path>`, `-v`/`--version`, `-h`/`--help`.** Previously the only flag was a single unnamed `(flag, arg)` pair. `--config` overrides which file `Config::load`/`Config::reload` (and the hot-reload watcher) read for the rest of the process, set once via a `OnceLock` before `Smallvil::new` runs. The old `-c`/`--command` (spawn one specific thing at launch) is renamed `-s`/`--spawn` -- freed up `-c` to mean config path, matching Hyprland's own flag exactly, since the old name would have collided with what a Hyprland-coming user expects `-c` to mean.

### Changed
- **Dropped the smallvil-scaffold behavior of auto-spawning `terminal` on every ordinary launch.** Traced via `git log --follow` to the very first scaffold commit -- it was Smithay's own minimal example's dev convenience ("spawn something so you have a window to test with"), never a deliberate daily-driver decision, and it directly defeated the new welcome hint (the desktop is never empty at startup if a terminal auto-spawns into it first). `-s`/`--spawn` (explicit, opt-in) is unaffected.

### Tests
- **Verified live, nested**: a fresh config produced the card centered on-screen exactly as designed (rounded cyan-bordered box, three lines of text) when the desktop was empty; spawning a window via the IPC socket (`tidectl spawn kitty`) made it disappear on the next frame with no explicit dismiss action needed. `--version`/`--help`/an unrecognized flag/`--config` with no argument all produced the right output and exit code; `--config <path>` pointed at a file with `gaps = 42`/`show_welcome_hint = false` loaded correctly (confirmed no file was written to the real `$XDG_CONFIG_HOME` location, and the welcome hint correctly stayed hidden). `cargo build`/`test`/`clippy` clean throughout.

## [0.50.0] - 2026-07-21

### Added
- **Keyboard layout config**: `xkb_layout`/`xkb_variant`/`xkb_options`/`xkb_model`/`xkb_rules` under `[input]`. Previously TideWM only ever compiled whatever `XkbConfig::default()` gives you (the system's `XKB_DEFAULT_*` env vars, typically US), with no way to run a different layout from config at all -- a real gap for anyone not on a US keyboard. Hot-reloaded (`KeyboardHandle::set_xkb_config`), same as everything else in `[input]`.
- **Touchpad config**: a new `[input.touchpad]` table -- `tap_to_click`, `tap_and_drag`, `drag_lock`, `disable_while_typing`, `natural_scroll`, `left_handed`, `middle_emulation`, `click_method`, `scroll_method`, `accel_speed`, `accel_profile`. TideWM's pinned `input` crate (libinput bindings) has exposed this entire API since day one; `src/input.rs` just never called any of it -- `DeviceAdded`/`DeviceRemoved` existed only for idle-notify gating. udev backend only, applied once per touchpad-capable device (`config_tap_finger_count() > 0`, the same check sway/Hyprland use) when libinput reports it.
- **Every touchpad field is opt-in (`Option`), not a forced default.** Leaving a key out of `[input.touchpad]` means "don't touch this setting," matching libinput's own "unconfigured means driver/hardware default" behavior -- not silently overriding a laptop's existing tuning with TideWM's own opinion.

### Fixed
- **`Seat::add_keyboard(...).unwrap()` at startup would take the entire compositor down on a keymap that fails to compile.** This was already latent (any `XkbConfig` could in principle fail), but adding user-controlled `xkb_layout` made it directly reachable by a config typo. Now: a failed compile is logged and falls back to the default keymap, which always compiles, instead of panicking. Same guarantee on reload -- a bad `xkb_layout` edit is reported and the previous, still-working keymap is kept, not replaced with nothing.

## [0.48.0] - 2026-07-20

### Added
- **A second tiling algorithm: master/stack (dwm/Hyprland's "master" layout), alongside the existing adaptive BSP engine.** This project's own existing default was already Hyprland's "dwindle" behavior in spirit (split orientation follows each leaf's aspect ratio) -- it just wasn't previously named as a distinct mode since it was the only one. Master/stack is genuinely new: one master window fills `master_ratio` of the area on the left, every other window splits the remaining height evenly on the right, always left/right regardless of output aspect ratio (unlike BSP's adaptive orientation -- that fixed split is the actual point of choosing this layout).
- **`default_layout = "bsp"` (or `"master"`)** top-level config key sets the starting algorithm for a workspace with no runtime override. `"Super+W"`/`"Super+Shift+W"` (`layout:bsp`/`layout:master` actions) switch the current workspace's algorithm at runtime; `"Super+Ctrl+Minus"`/`"Super+Ctrl+Equal"` (`master-grow`/`master-shrink`) nudge the master/stack ratio in steps, dwm/Hyprland's keybind-adjustable convention rather than click-drag (master mode has no BSP-style split boundary to click on in the first place).
- **The tree stays the same tree regardless of algorithm.** `layout::Layouts` keeps its existing `BspLayout` per (output, workspace) for membership/insertion/removal/swap/groups no matter which algorithm is active -- only the geometry computation (`Layouts::layout`) branches, reading the tree's own traversal order (`BspLayout::windows`) for master mode instead of its split shape. This is why focus-direction, swap-direction, window groups, fullscreen, and pseudo-tiling all keep working under master mode with zero changes: they're already geometry-based (via `Space`) or tree-shape-agnostic (leaf-content swaps), not BSP-split-specific. The one exception: `hit_test_split`/`resize_splits` (the drag-the-gap-to-resize feature) are BSP-split concepts with no master-mode equivalent, and now return `None`/empty whenever a workspace's algorithm isn't BSP, gated centrally in `Layouts` rather than at each caller.
- **Per-(output, workspace) algorithm and master-ratio overrides are pruned the same way, and for the same reason, `Layouts` already prunes empty trees**: both are keyed identically and reachable through the same IPC action surface, so leaving them unpruned would reopen the exact unbounded-growth-via-arbitrary-workspace-IDs problem the tree pruning comment already explains. Toggling a workspace to master, then closing every window on it, forgets the choice -- a deliberate trade for bounded memory over remembering a setting for a workspace with nothing left tiled on it.

- **Stale-socket recovery, found empirically while testing this:** `ipc.rs`'s `SocketGuard` only unlinks its socket file on a clean `Drop`, which a `kill -9` or a crash skips entirely -- confirmed live, a killed nested instance left its socket file behind, and a naive client would connect-and-fail with a confusing `ECONNREFUSED` while silently ignoring a genuinely-running instance's socket sitting right next to it. `tidectl` now removes a stale socket on `ECONNREFUSED` and retries once against whatever's left, only when it auto-discovered the socket itself (an explicit `--socket` is never second-guessed).

### Tests
- **Verified live against a nested TideWM instance:** every read query, `toggle-floating` and its own undo, the `workspace <N>` shorthand switching and reporting the right active workspace, an unknown action correctly rejected with a non-zero exit code, `--socket` explicitly targeting a known-good socket, and `--json` producing valid raw JSON. Also verified both edge cases around socket discovery: no socket present at all (clean, actionable error), and a `kill -9`-orphaned stale socket (detected, removed, honest "no TideWM socket found" once nothing valid is left).

## [0.40.0] - 2026-07-20

### Added
- **`wlr-output-management-unstable-v1`, hand-rolled on `wayland-protocols-wlr`** (Smithay 0.7 has no module for this one, unlike most protocols this codebase implements) -- the protocol kanshi, `wlr-randr`, and wdisplays need to read and change output layout at runtime. `src/handlers/wlr_output_management.rs` advertises every mapped output as a head (name/description/physical_size/enabled/current_mode/position/transform/scale, plus make/model/serial_number at v2+), and a client's `apply`/`test` transaction genuinely live-applies position/transform/scale changes -- real `Output::change_current_state` + `Space::map_output` mutation, not just protocol bookkeeping.
- **Deliberately doesn't support disabling a head or changing its resolution/refresh yet.** Both would need a real DRM modeset renegotiation on the udev backend, which is untestable in this sandbox (no real hardware) and the same risk class as `TileMoveGrab`'s 0.15.1 machine-freeze incident (shipped after only a code review, froze the entire machine on first real-hardware use -- see 0.15.1/0.16.0/0.24.1). Revisit once real hardware is available.
- Every currently-live head must appear in a transaction (enabled or disabled) or the client gets a protocol error (`unconfigured_head`), per spec. A configuration built against a stale `done` serial gets `cancelled` rather than silently misapplied -- the race-safety valve the protocol's serial exists for.

- **Verified live against a nested TideWM instance with a throwaway `wayland-client` test binary**, exercising the one part that actually needed verification, not just protocol round-tripping: a configuration that moves and rescales the (only, winit-backed) head is applied, and a second read-back of the head's `position`/`scale` events after `apply()` confirms the values genuinely changed -- not just that `succeeded` was sent. ### Fixed
- **Multi-monitor spawn bug: new windows opened on the wrong monitor.** Moving the mouse to a second monitor and pressing `Super+Enter` (or any spawn keybind) opened the new window on the monitor keyboard focus still pointed at, not the one the mouse was actually on. Root cause was the resolution order in `Smallvil::primary_output` (`state.rs`): it checked the focused window's output before the pointer's output, and `focus_follows_mouse` itself only shifts keyboard focus when there's a window under the pointer to shift *to* -- so a freshly-plugged or empty second monitor never won the comparison. ## [0.29.0] - 2026-07-20

### Added
- **`ext-session-lock-v1`, the first half of Phase H.** Lets a privileged client (swaylock, hyprlock) take over every output and gate all window/layer input until it decides to unlock -- TideWM had no real screen-lock story before this. The state machine (`state::SessionLock`: `Unlocked` -> `Locking(SessionLocker)` -> `Locked`) lives on `Smallvil` (`lock_session`/`unlock_session`/`register_lock_surface`/`mark_output_locked_frame` in `state.rs`); `handlers/mod.rs`'s `SessionLockHandler` impl is a thin adapter on top of it.
- **Confirmation waits for every output, not just one.** The `locked` event isn't sent until each output has actually rendered a locked frame (`Smallvil::locked_outputs`, distinct from Smithay's own same-named-but-unrelated per-output duplicate-`get_lock_surface` tracking) -- a single-output confirmation would leave a second monitor showing the unlocked desktop, exactly the leak the protocol exists to prevent. The "wait for lock surfaces to actually commit before starting to render" grace period real compositors (niri) add on top of that was deliberately cut: it only avoids a cosmetic blank-before-lock-UI flash, not a security gap, and this pass renders the blank fill immediately instead.
- **Both backends bypass their normal `render_output` convenience while locked**, rather than passing an empty window `Space`: `smithay::desktop::space::space_render_elements` pulls layer-shell content from `layer_map_for_output(output)` unconditionally, independent of whatever `spaces` it's given, so an empty `Space` alone would still have rendered a panel/bar on top of the lock screen. `Smallvil::lock_render_elements` (shared, called from both backends and from `capture.rs`) builds the lock surface's own content in front of a full-output opaque blank fill (`SolidColorBuffer`, same "commit counter only bumps on real change" pattern `Toast` uses) instead, and both backends call the lower-level `damage_tracker.render_output`/`DrmCompositor::render_frame` directly with just that list. `backend/udev.rs`'s `OutputRenderElements` enum gained one new `Lock` variant nesting `state::LockRenderElement<R>` as its payload, rather than two flat variants -- avoids an ambiguous `From<WaylandSurfaceRenderElement<R>>` impl colliding with the existing `Cursor` variant, and keeps the blank-vs-surface choice in the one shared function.
- **Screen captures (`grim`, anything on wlr-screencopy or ext-image-copy-capture) show the lock content too, never the desktop underneath.** `capture.rs`'s `render_one_capture` has its own separate render call from the visible-frame path (`AGENT.md`'s Phase E section already documents why: it needs the FBO/offscreen path, not the on-screen EGL surface) -- easy to miss, and initially missed during this pass, which would have let a screenshot tool read straight through the lock. Fixed the same way as the visible-frame paths: skip `custom`/`space` entirely and render `lock_render_elements` instead when locked, sharing the same readback/SHM-write tail either way (a security-sensitive bounded-pointer-write block, deliberately not duplicated).
- **Pointer and keyboard focus are lock-aware end to end, not just at lock time.** `KeyboardFocusTarget` gained a `Lock(WlSurface)` variant that `reconcile_keyboard_focus` gives absolute priority the moment `session_lock` isn't `Unlocked` -- clearing focus entirely (not leaking it to a window) until a lock surface registers. `surface_under` gets the same top-priority branch for pointer hit-testing, hard-coded to the lock surface (or nothing) rather than falling through to windows/layers. A new `Smallvil::refresh_pointer_focus` (a synthetic `pointer.motion` at the current location, no real device event) is called from `lock_session`, `register_lock_surface`, and `unlock_session` -- without it, a click or trackpad tap with no preceding real mouse movement would still hit whatever was focused before the transition, since Smithay only re-resolves pointer enter/leave on an actual motion event.
- **Interactive grabs are cancelled on lock, not just occluded.** `lock_session` calls `pointer.unset_grab` and releases any live popup grab before transitioning state -- grabs bypass `surface_under`-based routing entirely (Smithay dispatches directly to the grab's own callbacks), so an in-progress window drag would otherwise keep running, invisibly, underneath the lock screen.
- **Keybinds don't fire while locked; VT-switch still does.** `input.rs`'s keyboard filter closure gates the `config.keybinds` lookup behind `session_lock == Unlocked`, placed *after* the VT-switch check so Ctrl+Alt+F<N> stays a working escape hatch regardless of lock state -- that's a hardware/session-level operation a lock client shouldn't be able to withhold. `PointerButton` gets an unconditional early return mirroring the existing Exclusive-layer-early-return shape: forward the click to whatever `surface_under` already resolved and skip every WM action (raise, focus-window, grab-start).
- **A second `lock()` request while already locked is refused** (`lock_session` returns early; dropping the unused `SessionLocker` auto-sends the client `finished`, per protocol). Deliberately does *not* attempt to detect and take over from a dead lock client, even though the protocol allows it as compositor policy either way: Smithay 0.7's own `SessionLockManagerState::locked_outputs` (its per-output `get_lock_surface` duplicate-request guard) is only ever cleared on a graceful `unlock_and_destroy`, never on ungraceful client death, so a new client's `get_lock_surface` would still hit a `duplicate_output` protocol error (which disconnects it) even if this handler accepted its `lock()` call. Not fixable from the compositor side at this pinned Smithay version -- a crashed lock daemon leaves the session locked until TideWM restarts, the same "acceptable to be permanently locked" outcome the spec itself sanctions, just without the takeover niri/driftwm both attempt.
- **`zxdg_decoration_manager_v1` + `org_kde_kwin_server_decoration_manager`, the second half of Phase H.** Lets GTK/Qt clients ask whether to draw their own title bar (client-side decorations); without either protocol, a tiling layout could end up with unwanted client-drawn decorations on some apps that default to CSD. Both enforce server-side (which, since TideWM itself draws no decorations, means no decorations at all) -- the sway/Hyprland convention: a client-drawn header bar wastes vertical space in a tile, and floating windows focus/move/resize through Super-modifier actions rather than a title-bar hit-test. `request_mode`/`unset_mode` deliberately don't honor a client's ask for client-side; the protocol explicitly allows the compositor to disagree, and the configure that follows re-advertises server-side so well-behaved clients stop drawing CSD. Anvil honors client requests because anvil actually implements SSD drawing, which TideWM does not. Two protocols rather than one because Qt/KDE apps without xdg-decoration support speak the older KDE variant instead -- same enforcement shape, same effective behavior.
- **Per-app window rules (Phase K), minus opacity.** A new `[[window_rule]]` config section matches newly-mapped windows by `app_id` (exact) and/or `title` (case-insensitive substring) and applies a placement before the window's first tile/floating rect is ever computed: initial `workspace`/`output`, `float`, `pseudo_tile`, and `pin`. Multiple matching entries combine (`Config::resolve_window_rules`): `workspace`/`output` take the last match, `float`/`pseudo_tile`/`pin` accumulate (any match sets it -- booleans have no "unset" state to fall back to for an earlier match to lose to). i3/sway's `for_window`, Hyprland's `windowrule` -- same idea, TideWM's own config shape.

A new shared `Smallvil::toplevel_identity` (app_id/title from `XdgToplevelSurfaceData`) replaced a copy of the same lookup that used to live only in `ipc.rs`.
- Opacity was in the original Phase K scope but is dropped from this pass: `wp-alpha-modifier` turns out to be client-driven (a client sets its own surface's alpha; the compositor can't impose one via config through that protocol), so a real `window_rule.opacity` needs per-window alpha at render time -- `space_render_elements`'s single whole-space alpha parameter doesn't support that, and doing it properly means the same tier of render-path restructuring the fullscreen-above-layer-shell gap was held off for (see 0.13.0/AGENT.md's Fullscreen section). Not attempted here.
- **`xdg-activation-v1`, `wp-single-pixel-buffer-v1`, `wp-presentation-time`, and `wp-fractional-scale-v1` (Phase I).** `xdg-activation-v1` fixes focus handoff on request -- xwayland-satellite's startup log used to warn it couldn't bind this global at all. Token freshness follows niri's shape (fresh keyboard-or-pointer-enter serial required; a serial-less token is accepted outright rather than downgraded, since TideWM has no urgency indicator to fall back to and xwayland-satellite/notification daemons both routinely hand out tokens with no serial). Grant path (`Smallvil::activate_toplevel`) focuses the window, switches to its workspace first if hidden, promotes a parked group member, and raises it only if floating. `wp-single-pixel-buffer-v1` and `wp-presentation-time` are mostly handler-free at the protocol layer; the real work for the latter is `Smallvil::take_presentation_feedback` (modeled on anvil's own helper), called from both backends' render loops after a frame presents. `wp-fractional-scale-v1` fixes blurry rendering at non-integer output scales (1.25x, 1.5x) -- clients used to only ever see the integer-rounded `wl_output` scale.
- Landed on `ai/k3/phase-i-protocols` with no CHANGELOG/AGENT.md entries of its own -- backfilled here at merge time from the code's own (thorough) doc comments. Not independently live-tested as part of landing this; same code-review standard as everything else in this file that doesn't carry an explicit "verified live" note.
- **`wp-pointer-constraints-v1` + `wp-relative-pointer-v1` (Phase J).** Lets a client lock the pointer in place and read relative motion deltas instead (FPS-style camera look), or confine it to a region/surface (strategy games, modal menus). `PointerConstraintsHandler` (`handlers/mod.rs`) decides whether to honor a `new_constraint` request; enforcement itself lives entirely in `input.rs`'s `PointerMotion` arm, the only path that mutates pointer position. Relative-pointer is purely additive on top: one `pointer.relative_motion(...)` call per motion event, any client that bound `zwp_relative_pointer_v1` gets the deltas, nothing about existing clients changes. Constraint lookup walks the surface's subsurface-parent chain (new `Smallvil::root_with_constraint`/`surface_root`) rather than only checking the exact focused surface, since a constraint is typically registered on an xdg-toplevel while pointer focus may legitimately be on a subsurface of it -- a real improvement over Smithay's own `anvil` reference example, which only checks the focused surface directly and would miss that case.
- Closely follows `anvil`'s own reference implementation in shape (activate-if-already-inside-region-at-request-time, drop-the-motion-outside-region for confined rather than clamping to the boundary, emit relative motion unconditionally before checking for a lock) -- confirmed against anvil's actual source, not assumed. One notable case *not* implemented: anvil's `cursor_position_hint` repositions the compositor's pointer to help a locked-pointer client's own software cursor line up with what the compositor thinks the pointer position is; TideWM doesn't composite any cursor during a lock today (the system cursor is simply hidden), so there's nothing for that hint to line up with yet -- the handler hook exists, documented as a deliberate no-op, for whenever that changes.

## [0.26.0] - 2026-07-19

### Added
- **Screenshots work: both `ext-image-copy-capture-v1` and `wlr-screencopy-unstable-v1` are implemented, so `grim` (and anything else using either protocol) can capture an output.** This is the first half of Phase E from the roadmap; screencasting (pipewire + portal) is still unbuilt and shares the capture-buffer machinery introduced here. ext-image-copy-capture uses Smithay's `image_capture_source`/`image_copy_capture` modules (`src/handlers/capture.rs`); wlr-screencopy is hand-rolled on `wayland-protocols-wlr` (`src/handlers/screencopy.rs`) because Smithay has no convenience module for it -- same tier of work layer-shell was. Only output sources are supported (no per-window capture yet, since TideWM has no foreign-toplevel-handle protocol to map a client's `wl_surface` to one of its own `Window`s). SHM only: the `linux_dmabuf` wlr-screencopy offer is never sent, so dmabuf-path consumers don't yet work.
- **Region capture (`grim -g "$(slurp)"`) works** via the wlr-screencopy `capture_output_region` request, which ext-image-copy-capture-v1 has no equivalent for. The region is converted from output-local logical coordinates (what slurp reports) through the output's scale and transform into buffer space, then clamped to the output's bounds. ext-image-copy-capture sessions always capture the full output.
- **Both protocols share one render-and-readback path** (`src/capture.rs`): a frame request is validated and queued as a `PendingCapture`, then drained by the active backend's render loop (the only place a GL renderer is guaranteed to have a current EGL context). The drain renders the output exactly like the visible frame does (same `render_output` path the winit backend uses for the on-screen frame, so windows and layer-shell surfaces stack identically), copies the result into an offscreen `GlesTexture`, reads the pixels back into CPU memory, and writes them row-by-row into the client-provided SHM buffer. The completion event differs per protocol (`frame.success` for ext, `frame.ready` for wlr) but everything before that is protocol-independent. A backend cleanup tick (`cleanup_capture`) drops dead sessions and fails queued captures whose output went away (hot-unplug), which would otherwise sit in the queue forever.
- **Cursor compositing (`overlay_cursor`) is honored for the named-cursor glyph path** -- the xcursor theme / fallback dot TideWM itself draws on the udev backend. A client-set cursor surface (`CursorImageStatus::Surface`) is not composited yet; under winit the host compositor's cursor is never part of TideWM's own frame anyway, so capture passes `composite_cursor = false` there.
- **wlr-screencopy buffer validation is real.** The frame's `copy`/`copy_with_damage` request is untrusted client input: the buffer must be SHM, in one of the two advertised formats (`Argb8888`/`Xrgb8888`), and at least the offered size. Anything else fails the frame rather than risking a bad write later. The actual SHM row-copy uses bounded raw-pointer writes inside `with_buffer_contents_mut`, each length-checked against the pool length first -- the same intended-usage pattern Smithay's own docs describe, since constructing a Rust slice into a client-mutable pool is UB.
- **Laptop lid-switch and tablet-mode events now drive configurable actions.** A new `[switch_events]` config section accepts an action string for each of `lid_close`, `lid_open`, `tablet_mode_on`, `tablet_mode_off`, using the exact same syntax `[keybinds]` already does (`spawn:systemctl suspend`, `close-window`, `workspace:N`, anything `parse_action` accepts). The libinput switch events that used to fall through `process_input_event`'s catch-all as no-ops now update `Smallvil::is_lid_closed` / `is_tablet_mode` and dispatch the matching action through the same `run_action` keybinds and IPC use, so every existing action is also a switch-event action for free. Defaults are empty across all four: out of the box behavior is unchanged, opt in by editing the config. systemd-logind's own `HandleLidSwitch=` policy already triggers suspend on lid close independently of the compositor, so a `lid_close` entry here is for whatever extra you want on top of that, not a replacement for it. The dedup pattern (drop a switch event whose state matches what we already have) is the same one niri uses to absorb the redundant switch event libinput sometimes re-emits after a suspend/resume cycle, so e.g. closing the lid, letting the machine suspend, and resuming won't re-fire your `lid_close` action. Lid state is tracked but not yet used to disable the built-in panel when an external monitor is also connected -- that's a separate enhancement that needs per-output power management, which TideWM doesn't have yet (no DPMS).
- Udev backend only; winit's nested-session backend has no access to libinput's switch capability (no `InputEvent::SwitchToggle` ever reaches `process_input_event` there), so a nested session silently ignores the config section. Same standard as everything else udev-specific in this file: verified by careful reading against the pinned `smithay ff5fa7df` source, a unit test for the config parsing (action strings resolve, invalid ones are dropped to `None` without breaking the rest of the section), and clean build/clippy; not exercised with a real laptop with a lid switch under the udev backend.
- **Window groups/tabs.** `group-left/right/up/down` merges the focused tiled window with its neighbor into one shared tab slot (i3/sway's "tabbed container" idea); `cycle-tab-next`/`cycle-tab-prev` (default `Super+]`/`Super+[`) swap which member is visible; `ungroup` (`Super+Shift+G`) splits the focused tab back out to its own tile. New `tab_strip.rs` draws a thin bar along the top of a grouped leaf, one segment per member, the active one highlighted -- only for a leaf that's actually grouped, a solo tile is unchanged.
- Deliberately not a `layout::Node::Leaf(Window)` -> `Node::Leaf(Vec<Window>)` tree restructure, which would touch nearly every function in `layout.rs`. Follows this codebase's existing pattern instead: a group's leaf holds exactly one `Window` (the active tab), same as a plain tile, while `Smallvil::groups` tracks membership and each parked member's `Window` handle directly -- the same reason `FloatingTag` has to, since a hidden window isn't in `space.elements()` to re-find later. One small new `layout.rs` primitive, `replace_leaf`, swaps which `Window` a leaf holds, modeled on the existing `swap_leaves`.
- `detach_mapped_toplevel` (the single funnel every close/unmap path already routes through) is now group-aware: closing a group's active member promotes the next tab instead of collapsing the leaf, and closing the second-to-last member dissolves the group back to a plain tile.

- Multi-column layout, clamped to the narrowest connected output's width (`Smallvil::min_output_width`) so it wraps into more rows instead of rendering wider than the screen and clipping -- caught live during testing (a first pass sized purely off keybind count, and did exactly that on a 945px-wide nested output) and fixed before landing.

- **Fullscreen, maximize, floating, tiling, and pinning now have explicit restoration state.** Reasserting fullscreen is idempotent and never recaptures the output-sized viewport as a windowed restore rectangle. ### Fixed
- **Keyboard focus and XDG activation now have one authority.** Window clicks, empty clicks, focus-follows-mouse, cycling, directional focus, workspace hide/show, first map, null-buffer unmap, destruction, layer map/unmap, and compositor move/resize grabs all route through `Smallvil::reconcile_keyboard_focus`. Maximize and live move-grab updates therefore cannot silently activate a different window.

## [0.18.0] - 2026-07-18

### Added
- **Idle-inhibit and idle-notify** (Phase D of the WM feature-parity roadmap, see AGENT.md): `zwp_idle_inhibit_manager_v1` lets a client (video player, presentation app) hold an inhibitor; `ext-idle-notifier-v1` lets an external tool (a swayidle-style daemon) watch idle/resume transitions and act on them (screen off, lock, suspend). - **Idle-inhibitor cleanup was originally hooked to `toplevel_destroyed`, which is xdg_toplevel-specific** -- but the inhibit protocol takes any `wl_surface`, so a client abandoning an inhibitor tied to a surface that was never an xdg_toplevel would have left the whole compositor permanently unable to idle. ## [0.17.0] - 2026-07-18

### Fixed
- **Fullscreen state didn't reliably survive floating/tiled transitions or a cross-output workspace swap.** A tiled window that floated (or was moved to another workspace) while fullscreen could lose its pre-fullscreen restore rect, since the old code only ever captured `space.element_geometry` at the moment it left the tree -- which by then already reflected the fullscreen override, not the original windowed size. `FullscreenEntry::restore_rect` now survives a floating -> tiled -> floating round trip while still fullscreen (populated once via `remember_restore_rect`, preferring an existing floating rect, then the underlying tile rect, only finally the raw mapped geometry as a last resort), and `swap_workspaces` now moves each `FullscreenEntry` along with the tree content that owns it (`FullscreenEntry::move_to_output`, translating a saved floating rect by the delta between the two outputs' origins) instead of leaving fullscreen bookkeeping pointing at the wrong output after a swap. Added unit tests covering the restore-rect precedence.
- **The udev backend never waited for the renderer's own GPU fence before handing a frame to KMS.** `DrmCompositor::render_frame`'s result can report `needs_sync()` when KMS can't consume the fence directly; the swapchain image's fence is now waited on explicitly in that case before `queue_frame`, following the same contract Smithay's own `DrmOutputManager`, niri, and driftwm all honor.
- **A `queue_frame` returning `EmptyFrame` silently dropped the frame with no retry**, which could leave an animation or a client's own redraw stuck with nothing scheduled to show it. An estimated-vblank timer (`empty_frame_retry_pending`, keyed by a per-device retry generation so a surface torn down and recreated on the same CRTC can't have a stale timer match it) now re-renders once at the estimated next vblank instead of just giving up.
- **A client's DMA-BUF could still be busy (GPU still writing to it) when it committed the buffer.** A pre-commit hook (`add_pre_commit_hook`, installed in the new `CompositorHandler::new_surface`) now generates a readiness blocker from the buffer's implicit fence and holds the commit until it clears, instead of compositing a buffer the GPU hadn't finished producing yet. Installed as a pre-commit hook rather than in the regular `commit` callback because by the time `commit` runs, Smithay has already merged the surface's pending state -- too late to block anything.
- **`linux-drm-syncobj-v1` was being advertised without the acquire-point blocker Smithay 0.7 actually requires**, which is unsafe -- exposing the protocol implies that guarantee is honored. The advertisement is withdrawn until a real `DrmSyncPointBlocker` backs it; AGENT.md's udev-backend section updated to describe client dmabuf import as "with a pre-commit readiness blocker" instead of claiming syncobj support.

### Known gaps (not silently missing, tracked for follow-up)
- **None of the above five fixes have been run on real hardware yet.** They were built and verified to compile clean against the pinned `smithay v0.7.0` source, reference-checked against niri/driftwm/Smithay's own `DrmOutputManager` for the fence-wait and empty-frame-retry contracts specifically, but a DRM/TTY backend needs real DRM master on a free VT to actually exercise the timing conditions (fence contention, an empty first frame, a genuinely-busy dmabuf) these fixes respond to. The fullscreen/workspace-swap fix has unit test coverage for its restore-rect precedence logic, but the live floating/tiled/workspace-swap transitions themselves are code-reviewed only pending a nested-session or hardware pass.

## [0.16.0] - 2026-07-18

### Fixed
- **Root-caused the real-hardware freeze from 0.15.1's tiled-window drag-to-swap test.** `TileMoveGrab::drop()` called `seat.get_pointer().current_location()` from inside the grab's own `button()` callback -- already holding the same pointer mutex for the whole dispatch, a guaranteed self-deadlock confirmed against Smithay's own source, not just suspected. Fixed by tracking the pointer location from motion events instead (`last_location`), the same approach `move_grab.rs` already used. **The grab stays unwired from `input.rs`**: the deadlock is fixed, but this project's own bar for re-enabling anything touching an interactive pointer grab on the udev backend is a real-hardware retest under `timeout` at minimum, which this sandbox still can't provide.
- **All four pointer grabs hardened while in the same code.** Each compared a released button against a hardcoded `BTN_LEFT` instead of whichever button actually started the grab (`ResizeSurfaceGrab` is only ever started via `BTN_RIGHT`), and none guarded against the dragged window's client destroying it out from under the gesture.
- **A client with two mapped surfaces could crash the entire compositor.** `check_grab` only checked that a move/resize request's surface belonged to the same *client* as the grabbed one, not that it *was* the grabbed surface -- despite its own comment claiming otherwise -- so a second surface from the same client could piggyback a valid grab serial and hit an unconditional `.unwrap()` on the resulting space lookup. Both `move_request`/`resize_request` now bail gracefully instead (the surface can also legitimately have been unmapped by the time the request arrives).
- **A new toplevel with nowhere to go was silently orphaned** -- no protocol response, never inserted anywhere -- instead of being closed, unlike `layer_shell.rs`'s existing handling of the same no-output case.
- **`move_to_workspace` never reassigned keyboard focus after hiding the moved window.** `unmap_elem` doesn't touch focus itself; the fix was extracted into a shared `refocus_after_hide` helper now used by both `move_to_workspace` and `switch_workspace`.
- **`move_to_workspace`'s hide/show guard compared the target workspace against the output's *active* workspace, not the window's own current one.** A window already sitting on some other hidden workspace (from an earlier move) looked identical to "already there" under that comparison, silently no-opping a move that should have happened -- and re-finding its `Window` handle via `space.elements()` (which doesn't hold hidden tiled windows) could lose it from the tiling tree entirely. Fixed with new `Layouts::workspace_of`/`window_of`, which look through the tree itself instead of trusting `active_workspace`/`space`; the same fix applied to the floating branch.

### Known gaps (not silently missing, tracked for follow-up)
- **The deadlock fix and grab hardening are code-reviewed, not live-tested.** Reproducing the original freeze needs a real press-motion-release pointer sequence on real hardware, which this sandbox can't inject -- same structural limitation noted since `TileMoveGrab` was first built in 0.15.0. Don't re-enable the grab in `input.rs` without that retest.
- **`move_to_workspace` was verified live via a nested session + IPC**, unlike the other fixes in this entry: hiding the only window on a workspace clears focus to none instead of leaving it stuck; hiding one of two windows moves focus to the survivor; the no-op guard correctly leaves state untouched when a window is already where it's meant to go; switching to the target workspace shows the moved window mapped and focused again.

- **No runtime output hotplug.** Connectors are scanned once at startup; a monitor plugged in afterward is logged but not turned into a live output. Multi-monitor tiling layout itself is also still unbuilt (existing roadmap item).
- **Single-GPU only**, no multi-GPU render-node compositing (anvil's `DrmOutputManager`/`MultiRenderer` approach was deliberately not used -- more machinery than a single-GPU-at-a-time compositor needs right now).

## [0.4.5] - 2026-07-17

### Added
- Release profile tuning (LTO, single codegen unit, strip): 10.9MB binary down to 6.6MB.

### Investigated
- **Memory usage looked worse than Hyprland; measured it properly instead of guessing.** Turned out to be a measurement problem, not a real one: every test this session used a `cargo build` debug binary (157MB), and raw RSS numbers were dominated by Mesa's driver stack (`libLLVM.so` alone: 99.8MB RSS) being double-counted as if it were TideWM's own cost, when it's a shared library already resident from the host Hyprland. Measured with a release build and PSS (the metric that actually accounts for sharing): TideWM idle, no windows, ~46MB PSS vs the host Hyprland's ~144MB PSS (full rice: Quickshell, animations, blur). Documented the correct measurement method in AGENT.md/CONTRIBUTING.md so this doesn't get re-litigated on bad data next time.

## [0.4.4] - 2026-07-17

### Fixed
- **Floating windows kept falling behind the tiled layer.** `Space::map_element` always re-raises whatever it touches, even with `activate: false`, so `retile()` was silently pushing every tiled window back above a floating one on every call (any window open/close/resize/config-reload). Floating windows now get re-raised after every retile, and stay above the tiled layer as they should.
- **Clicking a tiled window also raised it above floating ones**, same underlying issue. Tiled windows never overlap each other by construction, so they don't need raising on click at all now, only their activation state changes.

## [0.4.3] - 2026-07-17

### Added
- **Compositor-level `Super+LeftClick`/`Super+RightClick` drag to move/resize floating windows**, matching Hyprland's convention. Only applies to floating windows (see `toggle-floating`); dragging a tiled window would just get overwritten by the next retile.
- **`Super+Tab` cycles keyboard focus** through every mapped window and raises it. Previously there was no way to reach a window fully covered by another one, since you can't click something you can't see.

### Fixed
- Keybind spawn failures (e.g. the default `weston-terminal` not being installed) now show an error toast instead of failing silently with only a log line.

## [0.4.2] - 2026-07-17

### Fixed
- **The previous redraw-gating fix (0.3.1) was incomplete: idle CPU was still pinned at ~99%.** It correctly skipped the expensive compose/submit work when nothing changed, but the scheduling mechanism around it was unbounded (`request_redraw()` re-firing as fast as the event loop could spin, with nothing throttling it). Replaced with a bounded 16ms calloop `Timer`, which can't fire faster than its re-arm duration by construction. Idle CPU dropped to ~2% and falling. See AGENT.md for the full story and why "check log frequency" wasn't enough to catch this the first time.
- **fastfetch (and anything else reading the raw process/binary name) showed `tidewm` instead of `TideWM`.** The compiled binary is now named `TideWM` via Cargo's `[[bin]]` override; the package itself stays lowercase `tidewm` per Rust convention.

## [0.4.1] - 2026-07-17

### Added
- **Floating-window toggle** (`Super+V` by default). A window not tracked by the tiling layout is floating; toggling removes/reinserts it and retiles the rest. Untiling keeps the window's current geometry, no jump.
- Interactive move/resize (dormant since the tiling engine landed) works again, scoped to floating windows only.

### Fixed
- **Newly opened windows didn't get keyboard focus** until clicked, so a window-scoped keybind (close, the new floating toggle) didn't work on a freshly opened window without clicking it first. Windows now auto-focus on map.

## [0.4.0] - 2026-07-17

### Added
- **Dynamic tiling layout engine** (`src/layout.rs`), dwindle-style: each new window splits the focused window's space, side-by-side or stacked depending on that space's own aspect ratio. Closing a window collapses its sibling back into place. Verified with real client windows (kitty), not just a clean build.
- **`gaps` config key** (default 8px), the pixel gap the tiling engine applies around each window. Hot-reloadable.

### Changed
- Every window is tiled now. Interactive move/resize is disabled until floating windows exist (see AGENT.md); dragging a tiled window would just get overwritten by the next retile.

## [0.3.1] - 2026-07-17

### Fixed
- **Redraw loop was compositing every frame unconditionally**, even fully idle, doing full GPU work and spamming clients with frame callbacks at display refresh rate for nothing. Now gated behind a dirty flag set by client commits, window mapping, drag/resize motion, focus changes, and active toasts; idle sits at a constant frame count instead of climbing forever.

## [0.3.0] - 2026-07-17

### Added
- **Config hot-reload.** `~/.config/tidewm/config.toml` is watched (parent-directory watch, so atomic save-via-rename editors trigger it too) and reloaded live: keybinds and keyboard repeat rate/delay apply without a restart.
- **First-party toast notification.** Confirms a reload (or reports a parse error) with TideWM's own on-screen toast, not a desktop notification daemon. CPU-composited RGBA texture (rounded pill, rasterized text), fades out after ~1.8s. Sets the pattern for future OSDs (volume, workspace switch, etc).

## [0.2.0] - 2026-07-17

### Added
